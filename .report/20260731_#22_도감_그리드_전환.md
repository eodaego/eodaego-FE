### 📌 작업 개요
도감 화면을 세로 리스트에서 3열 그리드로 전환. 카드 형태와 타이포를 그리드에 맞게 다시 짜고, 목록과 스켈레톤이 같은 칸 크기를 쓰도록 배치 로직을 한 곳으로 모았다.

### 🎯 구현 목표
- 도감을 한 화면에 더 많이 보여주는 3열 그리드로 개편
- 수집/미수집 시각 대비는 기존 규칙을 그대로 유지
- 요청받은 페이지네이션은 서버 계약을 조사해 필요 여부를 판단

### ✅ 구현 내용

#### 리스트 → 그리드 전환
- **파일**: `lib/features/collection/presentation/pages/collection_page.dart`
- **변경 내용**: `_CollectionList`(`ListView.separated`)를 `_CollectionGrid`(`GridView.builder`)로, `_CatalogListItem`(가로 `Row`, 원형 썸네일 56 + 이름 + 카테고리 + 우측 상태 마커)을 `_CatalogGridCard`(세로 `Column`, 원형 썸네일 64 + 이름 + 카테고리 라벨)로 교체
- **이유**: 그리드 레이아웃은 가로 행이 아니라 세로로 쌓이는 카드가 맞고, 칸이 좁아지는 만큼 썸네일을 키워 시인성을 유지

#### 그리드 배치 헬퍼 추출
- **변경 내용**: `SliverGridDelegate _gridDelegate()` 함수를 top-level에 추출 (`crossAxisCount: 3`, `mainAxisSpacing/crossAxisSpacing: 10`, `childAspectRatio: 0.8`)
- **이유**: 실제 목록(`_CollectionGrid`)과 로딩 중 스켈레톤(`_CollectionListSkeleton`)이 같은 `gridDelegate()`를 호출하게 해서, 로딩→데이터 전환 시 칸 크기가 흔들리지 않도록 함

#### 스켈레톤 그리드 전환
- **변경 내용**: `_CollectionListSkeleton`도 `ListView.separated`(8개) → `GridView.builder`(9개, `_gridDelegate()` 재사용)로 변경. 스켈레톤 카드 내부도 `Row` → `Column`으로 맞춤
- **이유**: 로딩 화면과 실제 그리드의 칸 배치를 일치시키기 위함

#### 카드 내부 스타일 조정
- **변경 내용**: 이름 텍스트 스타일을 `AppTextStyles.label16Semibold` → `AppTextStyles.tag13Bold`로 변경. 카드 `radius`는 `AppRadius.sm`(12)를 그대로 유지. 우측 체크 아이콘(`_stateMarker()`, `Icons.check_circle_rounded`)은 제거
- **이유**: 좁아진 3열 칸에 맞는 타이포 크기로 조정. 그리드에서는 카드 배경(surface/surfaceDim)·테두리 유무·이름 텍스트·색상만으로 수집 여부가 이미 구분되므로 별도 체크 마커가 불필요해짐

### 🔧 주요 변경사항 상세

#### `_CatalogGridCard`
`Material` + `InkWell` 위에 `Column`(가운데 정렬)으로 썸네일 → 이름 → 카테고리 라벨 순서로 배치. 수집 여부에 따른 대비 규칙은 기존과 동일하게 유지된다.

- 수집: `AppColors.surface` 배경 + `AppColors.line` 테두리 + 실제 이름(`tag13Bold`, `ink`색) + 카테고리 라벨(`category.dark`색)
- 미수집: `AppColors.surfaceDim` 배경 + 테두리 없음 + `'미수집'` 텍스트 + `'?'` 원형 썸네일 + `AppColors.uncollected`색 (이름·카테고리 라벨 모두)

**특이사항**:
- 썸네일 크기가 56 → 64로 커졌다. 그리드 칸이 좁아지는 대신 원형 썸네일을 키워 시인성을 보완했다.
- RefreshIndicator 관련 로직(빈 상태에서도 당겨지도록 `LayoutBuilder` + `SingleChildScrollView` + `AlwaysScrollableScrollPhysics`)과 에러/빈 상태 문구는 손대지 않고 그대로 유지했다.

### 📌 참고사항

#### 페이지네이션은 도입하지 않음 (검토 결과)
요청은 있었으나 서버 계약을 확인한 결과 도입하지 않기로 판단했다.

- `docs/api-docs.json` 전수 조사 결과 문서 전체에서 쿼리 파라미터는 `category`, `name`, `request`뿐이다. `page`/`size`/`cursor`/`offset`/`limit`/`hasNext`/`totalPages`나 Spring `Page<T>` 스키마는 어디에도 없다.
- 도감 목록 `GET /api/{version}/catalog`는 `CatalogItemListResponse`로 `items[]` 전체와 `totalCount`, `collectedCount`를 한 번에 반환하는 구조다. 클라이언트가 붙일 페이지네이션 계약 자체가 없다.
- 도감은 큐레이션된 고정 목록(문서 예시상 전체 `totalCount` 80)이라 현재 규모에서는 전체 조회가 더 유리하다고 판단했다. 페이지네이션을 도입하면 지금 로컬로 처리 중인 카테고리 필터·이름 검색이 페이지 단위로 깨지고, 헤더의 수집 뱃지(`collected/total`) 카운트도 어긋난다.
- 백엔드에 `page`/`size` + `hasNext`가 추가되고, `totalCount`/`collectedCount`가 필터 기준 전체를 유지하는 계약이 확정된 뒤 배선하는 게 맞다고 결론냈다.

#### 후속 과제
- 백엔드 페이지네이션 계약이 확정되면 무한 스크롤 배선 검토
- 서버가 이미 지원하는 `category`/`name` 쿼리 필터를 현재는 클라이언트가 로컬 필터로 처리 중 — 서버 필터로 옮길지는 별건으로 검토
